## Location controls

Open the saved-pins pane in Map or Dog Walking. The toolbar provides All Places, Walking, Sitting, Fit Visible, Center Home, Edit Details, Search, Backups and Clear Search. Walking and Sitting filter linked service categories; a home offering both appears in both filters. All Places clears the service filter and search. Fit Visible frames the matching saved places; Center Home focuses the selected place. These controls change the view, not geographic coordinates.

Search includes the display address, original intake address, matched provider/map address, pet names and service categories. An accepted local correction retains the original input as provenance instead of making it disappear from search.

Edit Details opens a cancelable native form for home name, display address, notes, pet name/species, linked pets and home/per-pet service roles. Scroll to additional pets. Save Details uses the existing preview/candidate/revision guarded transaction; Cancel or Escape discards form edits. An unsaved pin draft must be resolved before opening another editor. A modal editor also prevents competing agent mutations; repository reads remain available.

The form shows placement quality/source and original versus matched address. Editing the display address does not relocate the marker or re-geocode it. Moving a pin remains a separate explicit geographic edit. Pet identity is stable across linked homes: renaming a linked pet updates that pet's name everywhere; Detach removes this home's association, retaining the pet record and associations at other homes. Removing service roles replaces this home's current roles only. The prior home/pet/link/service snapshot is retained in place history.

## Saved routes

Use Saved Routes or Ctrl+Shift+O. Select a named route, inspect its endpoints, mode/objective, region, saved distance and endpoint-coordinate changes. Open recomputes against the current graph and policy; the listing itself works without reading the graph. Saved distance describes the previous snapshot, not a new solve.

Rename changes display metadata. Archive is reversible and retains intent/history; enable Including Archived, select it and use Restore before opening it again. Pages contain up to 100 stored intents; active/archive filtering applies within that page. Stored capacity remains 1,000 routes. Metadata changes retain endpoint IDs, coordinate snapshots, graph signature and metrics. Management uses expected revision, a bounded request identity and a replay receipt for the most recent action. A stale revision or reused request identity with different input is refused. Route history is bounded to 2,000 prior snapshots; reaching capacity produces a refusal, not silent history eviction.

## Private backup and recovery

Backups opens the native recovery dialog. Create Backup creates a consistent validated SQLite snapshot; Export JSON creates a readable copy of the canonical document. Both create new files in `pins/backups` under the active runtime namespace, use mode 0600 and never overwrite a prior destination. These files contain addresses, pets, services, routes, history and extension metadata. Map packs are excluded, so backup size tracks personal records rather than basemap storage. Existing files are never automatically pruned by this feature.

To restore, choose a recent snapshot or enter a separate absolute `.sqlite` path, then Preview Restore. Inspect its record counts before using Restore Backup. Changing the selected source clears the preview. The service checks SQLite identity/schema/integrity/foreign keys and bounds, the exact source payload token and the current workspace token. A changed source or stale workspace refuses the restore. Symlinks, corrupt/future-schema backups and read-only current stores are refused. This is recovery from a valid repository snapshot, not an arbitrary database repair tool.

Before replacing personal records, restore creates a consistent `places.sqlite.before-restore-<timestamp>.sqlite` recovery snapshot beside the current database. Canonical records and derived indexes are replaced in one guarded transaction; a failure preserves current records. The recovery snapshot remains selectable for undo. JSON export is readable archival/interchange output; native restore accepts the SQLite snapshot.

Supported structured operations are `routes.rename`, `routes.archive`, `repository.backup`, `repository.export`, `repository.restore.preview` and `repository.restore`, in addition to existing intake/place/route operations. Repository restore requires `source`, `source_token`, `expected_store_token` and `request_id`; route management requires `route_id`, `expected_revision`, `request_id` and either `name` or Boolean `archived`. The running native owner must include this slice before its inbox can handle new operations. Never send them to an older owner and interpret a source-tool build as activation.
